📌 背景与问题

推送通知是大规模平台的关键推荐场景——让系统在App之外主动触达用户，提升长期留存。但设计最优推送系统面临两个核心挑战：

挑战说明
复杂的动作空间需要同时决定"是否推送"和"何时推送"
系统资源约束推送频率和计算开销受严格限制

❌ 已有方法的局限

预规划频率法
离线建模分配推送时间
缺乏实时适应性
固定间隔触发法
定时轮询系统
计算开销大 vs 时机丢失的两难
多阶段框架
各阶段独立优化
陷入局部最优

💡 STEPS 核心方案

将推送推荐重新定义为自触发的智能体过程：系统不仅决定是否推送，还决定何时再次唤醒自己，形成闭环。

🧠 规划智能体 Planning Agent

基于 Decision Transformer，使用门控有序回归方法调度下次系统调用时间。不只是"推不推"，而是"下次什么时候再来检查"。

⚡ 执行智能体 Execution Agent

基于轨迹奖励决定是否发送推送。综合考虑用户状态、内容质量和历史反馈。

🛡️ 过滤智能体 Filtering Agent

轻量级守卫：控制计算开销，防止不合理的规划行为。单独贡献79.42%的算力节省。

🔑 关键创新点

1. 自触发闭环：首次将推送推荐建模为自触发智能体过程，系统主动决定下次调用时机，而非被动等待。

2. 三智能体架构：规划-执行-过滤三层协作，端到端优化，避免多阶段框架的局部最优问题。

3. 工业级验证：已在抖音全量部署，覆盖超10亿用户，线上指标显著提升。

4. 效率与效果平衡：过滤智能体在保证效果的前提下节省79%算力，使高频自触发成为可能。
