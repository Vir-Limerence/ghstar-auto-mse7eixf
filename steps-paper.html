1. 背景：推送推荐为什么难

推送通知是大规模平台上唯一能在App外主动触达用户的渠道。用户在刷抖音时不会收到推送——推送只在用户离开App后才起作用。因此，推送的设计直接影响长期留存和重新激活。

但设计最优推送系统面临一个经典的"是否 + 何时"两难：

🎯 动作空间复杂：系统必须在连续时间轴上同时决定——这个时刻要不要推？如果现在不推，那什么时候再检查？

⚡ 资源约束严格：每秒钟对所有用户做实时排序判断在工业系统中不可行。推送系统需要平衡效果、效率和用户体验。

😫 用户疲劳敏感：推送时机不当会导致用户直接关闭推送权限——这是不可逆的损失。

2. 已有方法为什么不够好

预规划频率法
Pre-planned Frequency
离线建模 → 整数规划求解最优频率和推送时刻 → 按时执行。

问题：不感知实时用户状态，错过高价值推送时机
固定间隔触发法
Fixed-interval Triggering
定时轮询系统 → 每次判断是否推送。

两难：间隔太短→算力爆炸；间隔太长→错过最佳时机
多阶段框架
Multi-stage Pipeline
各阶段独立优化 → 全局次优。

问题：前一阶段的决策限制后一阶段，陷入局部最优

3. STEPS 核心方案：自触发闭环

STEPS 将推送推荐重新定义为一个自触发的智能体过程。系统不再被动等待外部定时器唤醒，而是自己决定下次何时唤醒自己，形成一个完整的闭环：

触发 → 判断是否推送 → 规划下次触发时间 → 触发 → ...（闭环）

核心公式：在每个时刻 t，系统同时输出两个决策：

(at, Δt) = (πA(st, Rt), πP(st, Rt))

其中 at ∈ {0,1} 是执行智能体πA的推送决策，Δt > 0 是规划智能体πP生成的下次唤醒间隔，Rt 是目标回报（return-to-go）

三智能体架构

🧠 规划智能体 Planning Agent

职责：生成下次系统激活的时间间隔 Δt。是系统的"主动引擎"，让闭环自驱动成为可能。

核心创新① — 门控RTG机制 (Gated-RTG)：标准Decision Transformer中，高维状态特征会淹没低维的RTG信号（1维标量），导致模型"忽略"目标回报。STEPS提出用 Hadamard积（逐元素乘） 将RTG注入状态：egated = es ⊙ MLP(Rt)。RTG从"普通特征"升级为"门控信号"，强制模型关注目标回报。

核心创新② — 有序回归 (Ordinal Regression)：直接预测连续时间 Δt 不稳定（标签非高斯、长尾、误差容忍度非线性）。STEPS将连续空间离散为 K=100 个等频桶，用 BCE 损失逐桶预测，在线推理时平滑聚合得到精确 Δt。

损失: Lnext = Σk BCE(yk, zk)，其中 yk = 1[Δt > τk]
推理: Δt = Σk (τk − τk−1) · Sigmoid(zk)

⚡ 执行智能体 Execution Agent

职责：在规划智能体指定的时刻，基于实时上下文决定是否发送推送。

核心创新 — Bellman RTG 建模 (GAVE改进)：离线训练数据中的行为是次优的，直接用观测RTG做回归会导致偏差。STEPS引入Bellman方程学习 Q(s,a|λn)，并通过优势加权重新加权动作损失，引导策略向高Q值动作学习。

Q值学习: LQ = Σ (Rt+1 − Q(st,at|λn))²
策略加权: wt = Sigmoid(α·(Q(a)−Q(1−a)))
策略损失: Lπ = −Σ [w'·log π + (1−w')·log(1−π)]

🛡️ 过滤智能体 Filtering Agent

职责：在请求到达昂贵的执行智能体之前，用轻量模型筛选掉低价值请求，同时拦截不合理的规划行为。

关键设计：用3层MLP + 仅用户和环境特征（排除物品特征），避免触发下游昂贵的物品排序管线。执行智能体处理物品排序时，每1k请求的算力是过滤智能体的57倍。

双重边界控制：系统侧（推送后短时间抑制）+ 用户侧（用户刚活跃后抑制），用分钟级保守阈值防止极端case。

6. 关键技术深度分析

6.1 门控RTG为什么重要

标准Decision Transformer中，1维RTG标量与高维状态拼接后容易被淹没——神经网络直接绕过RTG信号。STEPS的门控RTG用逐元素乘法强制状态被RTG调制，使模型的RTG相关性比从随机波动稳定收敛到约1.8（匹配训练数据真实统计）。

6.2 Bellman RTG vs 观测RTG

在线A/B显示：直接学习观测RTG的方法初期有提升但随后衰减至接近零；Bellman RTG建模持续稳定上升。原因在于离线数据中的历史行为是次优的，Bellman方程能纠正这种偏差，学习真实的累积价值。

6.3 过滤阈值敏感性

过滤智能体的阈值直接影响触发间隔。实验发现：间隔从0增到20分钟时，QPS显著节省且UAD几乎不降——这是最佳效率区间。但超过60分钟后UAD急剧下降。线上采用保守的分钟级阈值。

7. 工程落地挑战与解决方案

挑战1：实时事件与规划时间的融合

平台上有大量实时业务事件（关注创作者开播、好友发新视频等）。纯依赖规划智能体可能错过这些高价值时机。STEPS将事件驱动触发与智能体规划时间无缝融合，确保响应性和全面性。

挑战2：百万QPS下的算力预算

过滤智能体是核心解决方案。执行智能体处理物品排序时，每1k请求消耗的算力是过滤智能体的57.72倍。通过在早期用轻量MLP（仅用户和环境特征，不含物品特征）筛掉低价值请求，避免了触发昂贵的排序管线。

智能体每1k请求相对算力
过滤1.00x
规划1.27x
执行57.72x

挑战3：在线策略可调节

STEPS在训练时对 λn（正负奖励权重）从均匀分布 U(0,1) 中采样，使策略在不同目标权衡下都有效。上线后可以无需重新训练，直接调整 λn 来改变推送策略的激进程度。

8. 核心创新总结

1 自触发闭环范式：首次将推送推荐建模为主动的自触发智能体过程，系统自主决定下次激活时间，而非被动等待。

2 门控RTG：用逐元素乘法将目标回报注入状态，解决高维特征淹没低维条件信号的问题。

3 有序回归时间生成：将连续时间预测转为有序分类，100个等频桶在密集短间隔区域分配更细分辨率。

4 Bellman RTG价值学习：用Bellman方程纠正离线数据中的次优行为偏差，实现持续的长期价值提升。

5 轻量过滤守卫：用3层MLP在早期截断低价值请求，避免触发57倍算力的排序管线，独立贡献79%的算力节省。

6 工业级验证：抖音全量部署，14天在线A/B，10亿+用户，三大指标全面正向。
