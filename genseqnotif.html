一、CQL为什么不行

白话

LinkedIn之前用CQL（Conservative Q-Learning）来决定每条通知发还是不发。CQL基于TD学习——每次看"当前状态→当前奖励+未来价值"来更新Q值。但在大规模工业场景中，CQL有三个致命问题：训练不稳定（超参数稍微一变结果天差地别）、特征扩展困难（想加点新特征模型就崩）、可复现性差（同样的数据训练两次可能策略完全不同）。

白话类比：打麻将 vs 复盘

CQL像打麻将——每出一张牌都要评估当前局面的优劣（TD学习），牌局千变万化，同一个局面不同人打出的策略完全不同。Decision Transformer像赛后复盘——把整局牌记录下来，分析"如果我想要赢100分，每一步应该怎么打"——这是监督学习，稳定得多。

CQL的三个致命弱点：

① 训练不稳定：TD学习对超参数极度敏感，在高维推荐特征空间中经常发散或收敛到差解。

② 特征扩展困难：扩大状态表示的特征空间（如加入更多用户行为信号）常导致CQL训练崩溃——在LinkedIn的实验中，尝试给CQL增加特征直接导致无法训练出有效策略。

③ 可复现性差：同一数据训练两次可能产出行为完全不同的策略，增加了评估和迭代的成本——LinkedIn报告需要测试3倍以上的候选模型才能找到有效策略。

❌ CQL (保守Q学习)

TD学习 → 不稳定 · 特征敏感 · 难复现 · 需要3倍候选模型。特征维度扩展10倍就直接崩。

✅ Decision Transformer

回报条件监督学习 → 稳定 · 特征可扩展10倍 · 高度可复现 · 可调目标回报。

二、问题定义：通知决策的RL建模

白话

LinkedIn的通知系统叫ATC（Air Traffic Controller，空管员），每时每刻都有大量通知候选进入。ATC按固定节奏（比如每N分钟）批量处理：先对每个用户的所有候选通知打分排序，选出Top-1，然后交给决策智能体——发、发成badge还是不发。

状态 S：精心设计的特征集合，包括过去x小时的通知发送数量和类型、用户画像属性、距上次访问的时间、历史访问率、通知内容理解、用户和候选通知的上下文信号。

动作 A：三个离散动作——发push通知、发应用内badge、不发送。每个候选通知有一个"合格动作集合"（EAS），可能只有1个、几个或全部动作可选。

多目标奖励 r_t ∈ R^{|R|}：两类奖励——

① 预测型奖励：来自已有排序模型预测的CTR、打开率等，虽然引入偏差但大幅降低离线学习方差。

② 实际型奖励：用户在两次决策间的真实访问行为，加上自适应的通知量惩罚（防止过度骚扰）。

三、将通知流切成"片段"

白话类比：电影分镜

用户的通知交互是一段永不结束的连续剧（infinite horizon）。DT不能处理无限长的序列，所以需要把连续剧切成固定长度的"片段"。每个片段包含T步历史上下文 + H步前瞻窗口——就像看一部电影时，每次只看T分钟回顾+H分钟预告。

轨迹表示：

τ = (s1, R1, a1, r1, ..., sT, RT, aT, rT)

其中 T 是上下文长度，H 是前瞻窗口。对每步t，RTG计算为：

Rt = Σl=0H γl · rt+l

γ 是折扣因子——离现在越远的奖励权重越小。H提供"短期vs长期"的trade-off。

多维度保留reward：与常见做法不同，GenSeqNotif保留了多目标奖励向量 r_t ∈ R^{|R|}，而不是用一个标量λ加权合并。这让DT自己学习reward之间更复杂的组合关系，而不是依赖人工预设的线性权重。

四、量化回归回报提示：让模型学会"要多少分"

白话类比：点菜时的预算

原始Decision Transformer需要手动指定"期望回报"（RTG），就像你进餐厅说"我今天预算300块"——但如果预算说的是"1000块"，厨师会懵（超出合理范围模型会瞎输出）。而且LinkedIn的CTR等奖励不是即时实现的——你发了通知后，用户可能1小时后才点击，但你需要在那之前就做下一个决策。

GenSeqNotif的做法是不让用户自己说预算，而是让模型学会"在当前状态下，合理的预算范围是多少"——就像服务员看到你的穿着、表情、同行人数，自动估算你大概会花多少钱。

核心创新：分位数回归学习回报分布

DT不仅要预测动作，还要学会预测"在当前状态下，第α分位数的RTG是多少"。训练时固定M个分位水平{α_j}：

Ŵt = MLPR(hRt) ∈ Rn_r × M

其中 h^R_t 是DT中RTG token的隐状态，n_r = |R| 是奖励维度数。预测值 Ŵ_t 的每一列对应一个分位数的回报估计。

Pinball Loss（分位数损失）：

LRTG = Σt=1T Σi=1n_r Σj=1M ρα_j(Ŵ(i,j)t, R(i)t)

其中pinball loss定义为：

ρα(ŷ, y) = { α·(y−ŷ) if y ≥ ŷ; (α−1)·(y−ŷ) if y < ŷ }

Pinball loss的妙处：它对高估和低估的惩罚不对称。α=0.75时，低估（预测低于真实值）惩罚0.75，高估只惩罚0.25——这鼓励模型"保守一点"，符合风险管理直觉。

推理时的线性插值：训练只学了M个离散分位数，但推理时可以用任意α：

Ř(i)t(α) = λα · Ŵ(i,l)t + (1−λα) · Ŵ(i,u)t
λα = (αu − α) / (αu − αl)

u是大于α的最小训练分位数索引，l是小于α的最大训练分位数索引。

动作预测：用合格动作集合(EAS)嵌入与隐状态做逐元素乘：

Laction = Σt=1T CrossEntropyLoss(at, ât)

总损失：

LDT = Laction + λ · LRTG

五、生产级工程：环形缓冲区和云端推理

白话类比：环形录像机

每个用户的通知交互序列需要持久化存储，但全量存储成本太高。LinkedIn的方案像一个环形录像机：固定存最近K条记录（K=16），新记录覆盖最老的记录，同时每条记录带时间戳以便恢复真实顺序。存的数据是"FLS tensor"（Float/Long/String），用zstd压缩后体积仅原来的1/5。

环形缓冲区设计要点：

① 物理存储不是时间序（环形覆盖），但每条带timestamp，推理时按时间重建。

② 部分更新API：推理后只写回当前步的新tensor，不重写全序列。

③ 选择性历史使用：通过String tensor中的key，可以忽略部分/全部历史——用于模型升级或特征变化时。

④ 维护工作流：Apache Airflow定期清理14天以上旧记录（TTL），大版本升级时全量清空。

⑤ zstd压缩：5倍压缩比，在存储配额内支撑全量用户。

云端推理隔离：每个模型运行在独立租户环境，简单模型用CPU，复杂模型上GPU/高性能CPU。多模型并行A/B实验互不干扰。

七、从CQL到DT：四个关键教训

教训1 — 特征可扩展性：CQL对特征维度极度敏感，扩展特征空间经常导致训练崩溃。DT天然适应高维特征，LinkedIn将特征维度扩展了超过10倍，DT反而获得显著性能提升。在真实推荐系统中，快速迭代特征空间是持续提升的基础。

教训2 — 稳定性 = 效率

CQL训练两次可能产出完全不同的策略，意味着需要测试3倍以上的候选模型。DT的高度一致性让所需候选模型减少到原来的1/3——从"大海捞针"变成"精准打靶"，大幅加速实验周期。

教训3 — Prompt调优 = 策略调优：分位数回归让DT的行为变得透明可解释。调整α值就能直接改变策略——α=0.5保守，α=0.95激进——不需要重新训练。这让策略调优从"炼金术"变成"旋钮调节"。

教训4 — 离线监督 = 在线强化：虽然DT用监督学习训练（比RL稳定得多），但通过回报条件（return-conditioning）隐式地进行了"如果我想要高分，我应该怎么做"的强化推理——用监督学习的方式，实现了RL的效果。

九、总结

1. DT替代CQL：把RL重新框架为回报条件监督学习，彻底解决了CQL的不稳定/不可复现/特征敏感三大问题，sessions +0.72% 且 通知量 -1.68%。

2. 分位数回归：不手动指定目标回报，而是让模型学会回报的条件分布。Pinball loss的不对称惩罚 + 推理时线性插值实现了训练后灵活可控。

3. Prompt调优：调整α值就能控制策略——α=0.5保守到α=0.95激进——不需要重新训练，CTR随之系统性变化。

4. 多目标向量：保留多维度reward而非标量合并，让DT自主发现reward间的复杂交互，推理时还可按cohort独立调节。

5. 环形缓冲区：固定K=16的FLS tensor持久化 + 带timestamp的时间序重建 + zstd 5x压缩 + 部分更新API，支撑150K QPS。

6. 特征扩展10倍：DT的监督学习范式天然适应高维特征——这对持续迭代的推荐系统是决定性优势。
