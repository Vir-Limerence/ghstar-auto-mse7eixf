一、CQL做推送决策有多痛苦

白话

LinkedIn之前用CQL（Conservative Q-Learning）做推送的发/不发决策。CQL是offline RL的经典算法，在学术上表现很好。但上了生产就各种翻车：训练不稳定、这次跑和下次跑结果完全不同、出了bug根本解释不清为什么这么决策。而且CQL对高维特征极其敏感，想加几个新特征模型就崩了。

❌ CQL的三大痛点

① 训练不稳定：TD学习对超参数极其敏感；② 不可复现：同样的数据跑两次可能行为完全不同；③ 不可解释：Q值为什么是这个数？说不清。

✅ DT的优势

① 监督学习范式：稳定、可复现；② 返回条件化：通过prompt调节行为目标，透明可控；③ 支持高维特征：特征维度扩展10倍都能稳定训练。

技术表述：离线RL方法如CQL基于TD学习——在Bellman backup中用保守估计避免高估。这在大规模推荐系统中面临三个瓶颈：(1) 训练不稳定性——TD学习对超参数和分布偏移敏感；(2) 可复现性差——相同数据不同run输出截然不同的策略；(3) 可解释性弱——高维状态空间下Q值难以归因。DT将RL重构为return-conditioned序列建模，用监督损失替代TD error，从根本上解决这些问题。

二、Decision Transformer 推送建模

白话

DT把推送决策建模成一个序列生成问题：看看过去几轮用户的状态 → 判断当时的回报到哪了 → 决定现在发不发。核心公式是(st, Rt, at, rt)——每一轮记录四个东西：当前状态、目标回报、做了什么、拿到了什么回报。

轨迹表示：

τ = (s1, R1, a1, r1, ..., sT, RT, aT, rT)

其中Rt是回报到Go (Return-To-Go)，定义为Rt = Σl=0H γl rt+l。H是前瞻窗口（look-ahead horizon），γ是折扣因子。

三个核心元素：

  • States st：过去x小时发送的通知数量和类型、用户画像、距上次访问的时间、访问率、通知内容理解等精心设计的特征集。
  • Actions at：三选一——发badge通知、发push通知、不发。
  • Rewards rt：多目标向量，包含预测的通知价值（点击概率）和真实用户访问行为。DT保持多维reward结构而非预定义线性加权——让模型自己学习复杂的reward组合关系。
关键设计：非episodic任务的Trajectory化

推送是连续无限长的（用户一直接收通知），没有"一局结束"的概念。DT的做法：从连续交互流中采样长度为T+H的窗口——T是上下文长度（看多少历史），H是展望长度（看多远未来）。滑动窗口生成重叠trajectory，让DT既能看历史又能规划未来。

三、Quantile Regression：让模型自己学"目标应该多高"

白话

原始DT需要你手动设一个"目标回报"——比如"我想要CTR 5%"。但这在推送场景里根本说不清该设多少：设太高模型产生幻觉，设太低模型懒得动。GenSeqNotif的方案：让模型学会预测"在当前状态下，各种分位数的回报是多少"，推理时你只需要说"我要75分位的CTR"，模型自己算目标。

训练：学习条件分位数分布

预定义M个分位数水平{αj}j=1M ⊂ (0,1)，模型学习：

Q̂R(i)(αj; τ<t, st) ≈ Q*R(i)(αj; τ<t, st)

用Pinball Loss（分位数损失）做回归：

LRTG = Σt Σi Σj ρα(Q̂(i,j)t, R(i)t)
ρα(ŷ, y) = α·(y−ŷ) if y≥ŷ else (α−1)·(y−ŷ)

总损失为动作损失 + RTG损失的线性组合：LDT = Laction + λ · LRTG

推理：线性插值实现任意分位数Prompt

虽然训练只学了有限M个分位数，推理时可以通过线性近似预测任意分位数α的RTG：

R̂(i)t = Q̂(i)t(α) = λαQ̂(i,l)t + (1−λα)Q̂(i,u)t, λα = (αu−α)/(αu−αl)

这就是Prompt Tuning的魔力——不需要重新训练，只改变α值就能生成不同激进程度的推送策略：α=0.5保守发，α=0.95激进追求高CTR。

Prompt Tuning 案例

实验证明：CTR prompt的分位数越高，在线CTR越高。从α=0.5到α=0.95，每个点对应一次独立A/B实验，CTR单调上升。这意味着运营人员可以直接用一个可解释的参数（"我要第95分位的CTR"）来控制策略行为，而不是调一堆看不懂的超参数。

Circular Buffer设计：每个用户维护K=16个历史tuple（FLS张量：Float/Long/String），按round-robin覆盖最旧记录。zstd压缩使存储减至1/5。两个后台Airflow流程：(1) Empty Push——大版本升级时清空；(2) TTL Repush——定期删除14天以上旧数据。

模型服务隔离：每个模型跑在独立tenant，简单模型用CPU、复杂模型用GPU。这样可以在线同时实验多个模型变体，互不干扰。

六、与STEPS的对比与关系

STEPS

三个Agent协同：规划师(Plan)+执行官(Act)+守门员(Filter)，用自触发闭环做推送时机决策，核心是"什么时候醒来检查"。

GenSeqNotif

单一DT模型：用return-conditioned序列生成一次完成发/不发/发什么类型的决策，核心是"在序列上下文里怎么做决策"。

深度联系

共同基因：都使用Decision Transformer范式。STEPS的规划智能体用门控RTG+有序回归做连续时间预测（下次多久后再来），GenSeqNotif用分位数回归做多目标RTG预测（当前该不该发）。

可组合性：

  • STEPS的规划智能体设定推送间隔Δt → 时间到了触发
  • GenSeqNotif的DT执行智能体在当前时刻做多目标发/不发决策
  • 两者对接：规划师定"什么时候检查"，DT定"检查后发什么/发不发"

工业启示：LinkedIn的CQL→DT迁移的经验对STEPS有直接参考价值——DT比TD-based RL在训练稳定性、特征扩展性、可解释性上都有显著优势，尤其是生产环境的可维护性。

八、总结与创新点

1. DT替代CQL：首次在LinkedIn生产推送系统中用DT替换value-based RL，sessions +0.72%同时通知量减少−1.68%。

2. 分位数RTG回归：用Pinball Loss学习条件RTG分布，推理时通过Prompt Tuning实现可解释的策略调节。

3. 非episodic轨迹化：从连续无限交互流中采样T+H窗口，让DT适配推送场景的无限horizon特点。

4. Circular Buffer生产设计：KV store + 16步round-robin历史 + zstd压缩 + 部分更新，支撑150K QPS在线推理。

5. 工业级经验：CQL→DT的迁移教训——训练稳定性、特征扩展性、可复现性、策略可调性是工业RL的核心维度。
